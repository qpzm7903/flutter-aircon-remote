# v0.2.0 — 多空调设备、配对测试向导、按设备的功能显示

设计依据：[架构设计 §12–§19](../architecture.md)。本文给出范围、用户故事、验收标准、迁移说明与测试清单。

## 1. 背景（用户反馈与根因）

反馈（译）：“怎么发现空调？打开时好像找到了两台，但没找到其他房间的——是不是因为我没走过去？是否该有空调检测功能？另外要能给每台空调命名，不然不知道是哪个位置。还有，按钮/功能是怎么确定的，写死的吗？”

根因：v0.1 **没有“设备”概念**。遥控页的下拉里有“格力 Gree / YAW1F”“格力 Gree / YBOFB”两项，其实是**同一品牌的两种遥控协议变体**，被误读为“发现了两台空调”。红外是**单向**的，手机既不能发现也不能检测空调。

结论：①引入设备；②用“添加空调 / 配对测试”向导代替不可能的自动检测，并在界面里明说原因；③协议型号改称“遥控协议型号”，放进设备设置；④按钮由“协议能力 ∩ 用户设置”数据驱动，并提供“按钮说明”。

## 2. 范围

**包含**
- 多台空调（`AcDevice`）：名称（必填）、房间（可选）、图标、遥控协议型号、独立状态、功能显示覆盖、排序。
- 首页空调列表：空状态说明、添加 / 编辑 / 删除（二次确认）/ 拖拽排序。
- 添加空调向导（含红外单向说明）与配对测试：依次尝试 Gree 的 YAW1F、YBOFB、YX1FSF 探测帧，用户确认“滴声”；全部失败仍可保存并给出排查提示；设置页可重新配对。向导逻辑为纯状态机。
- 新增 Gree **YX1FSF** 协议变体（= YAW1F + Econo“节能”模式）。
- 设备设置页：名称/房间/图标、遥控协议型号、功能显示开关（模式 / 风速 / 扫风 / 附加功能 / 温度范围）、删除。
- 隐藏功能在发送帧中的归一化规则；遥控页、设置页的“按钮说明”。
- 持久化 schema v2；v0.1 数据迁移为一台“我的空调”（幂等）。
- 版本 0.2.0（pubspec、常量、README、plan、版本测试）。

**不包含**：自动发现 / 真实状态读取（物理不可行）、红外学习、云同步、多品牌（仍只有 Gree）、定时、分组/批量控制、设备导入导出、桌面小组件。

## 3. 用户故事

1. 作为家里有多间卧室的用户，我想给每台空调起名字（主卧、书房、客厅），这样我知道在控制哪一台。
2. 作为第一次打开 App 的用户，我想看到“为什么没有自动发现空调”的解释和明确的添加入口，而不是一个令人误解的下拉。
3. 作为新增空调的用户，我想让手机对着空调发一条测试信号，听到“滴”声就确认，以便选对遥控协议。
4. 作为遥控器型号不明的用户，如果三种测试都没响应，我想看到排查建议，并仍能保存以便稍后再试。
5. 作为已配对用户，我想在设置里重新做配对测试或手动改“遥控协议型号”，而不必删除重建。
6. 作为我家空调没有指示灯 / 没有扫风 / 没有换气功能的用户，我想把这些按钮隐藏，界面更简洁，也避免误操作。
7. 作为不明白某按钮为何灰了或不见了的用户，我想打开“按钮说明”看到原因（协议不支持 / 我隐藏了 / 当前模式不可用）。
8. 作为 v0.1 的老用户，升级后我想保留原来的空调状态，不丢设置。
9. 作为用户，我想拖动调整空调的顺序，并在删除前被确认。

## 4. 验收标准

### 4.1 设备与首页
- AC-1 首次安装（无遗留数据）：首页显示空状态，标题“还没有添加空调”，说明红外单向、无法自动发现，并有“添加空调”按钮。
- AC-2 添加后首页出现设备行：图标、名称、副标题“房间 · 格力 Gree / 型号”（无房间则省略房间）；重启后保留。
- AC-3 名称必填且 1–20 字；允许重名；房间可选（≤20 字）；最多 20 台，满额时“添加”禁用并有提示。
- AC-4 删除需确认对话框；取消不删除；确认后设备及其状态键均被清除；正在打开的该设备遥控页收到通知并返回。
- AC-5 拖拽排序后顺序立即变化并持久化（`sortOrder` 重排为 0..n-1）。
- AC-6 点击设备进入其遥控页：AppBar 显示设备名；遥控页**没有**协议下拉；两台设备状态互不影响。

### 4.2 配对向导
- AC-7 向导第一页明确说明“红外是单向的，手机无法自动发现或检测空调；需对准空调、几米内”。
- AC-8 测试顺序为注册顺序 YAW1F → YBOFB → YX1FSF；每次发送一帧探测帧（开机·制冷·26 °C·风速自动·灯亮；YX1FSF 为节能模式 26 °C），字节与 §17.4 一致。
- AC-9 按钮：“有响应”→保存该变体并结束；“没反应，试下一个”→发送下一个变体；“重发”→重发当前；所有变体失败→显示排查提示，并可选择一个型号“仍然保存”或“重新测试”。
- AC-10 向导保存之前，**任何持久化数据均不变**（含已有设备状态）；中途取消不留下任何记录。
- AC-11 无红外手机：显示无红外横幅；可填信息，配对步骤只能“跳过”（以首个变体保存，标记未确认）。
- AC-12 设置页可“重新配对测试”，结果仅写入设置草稿，点“保存”后才生效；不改名称/房间/状态之外的数据。
- AC-13 向导状态机为纯逻辑（无 Flutter / IO / 计时），同输入同输出；过期的发送结果被忽略。

### 4.3 数据驱动按钮
- AC-14 每个控件是否显示 = 协议能力声明 ∩ 设备覆盖；是否可点 = 再叠加当前模式规则。三种 Gree 变体的声明独立（仅 YX1FSF 有“节能”模式）。
- AC-15 设置页每个功能一个开关，关闭后遥控页立即不显示；模式与风速至少保留一个；扫风可整体关闭；温度范围可缩小。
- AC-16 隐藏的功能发送时为中性值：灯光=亮，强劲/换气/睡眠/温度显示=关；隐藏的当前模式/风速/扫风位置回落到可用项；温度夹取到范围内。设置变化只更新状态，不发码。
- AC-17 “按钮说明”列出每个控件的状态：可用 / 已隐藏 / 此协议不支持 / 当前模式不可用，并含规则说明；与实际显示一致。
- AC-18 设置页该选项文案为“遥控协议型号”，并说明“同一品牌的不同遥控编码，不是不同的空调”。

### 4.4 迁移与版本
- AC-19 v0.1 升级：存在 `remote.protocolId` 或 `remote.state.*` 时，首次启动生成一台“我的空调”（id `legacy-1`），协议为原所选协议（缺失则 yaw1f），状态为该协议的旧状态（缺失则默认）；其他协议的旧状态丢弃；启动不发码。
- AC-20 迁移幂等：写入顺序为 state → index → schemaVersion(2)；schema 已为 2 时完全不触碰存储；中途失败重启后重试结果相同；旧键保留不删。
- AC-21 数据损坏（JSON 损坏、类型错误、索引损坏）不崩溃、不弹错误，回落默认并记 WARN；索引损坏时原文备份到 `device.index.corrupt`。
- AC-22 版本号 0.2.0 在 `pubspec.yaml`、`AppConstants.version`、README、文档中一致，`version_test` 通过。
- AC-23 `flutter analyze` 零问题，`flutter test` 全绿，架构测试通过，release APK 构建成功。

## 5. 迁移说明

| 项 | v0.1 | v0.2 |
|---|---|---|
| 设备 | 无 | `AcDevice`，存 `device.index` + `device.state.<id>` |
| 协议选择 | `remote.protocolId`（全局） | `AcDevice.protocolId`（每台） |
| 状态 | `remote.state.<protocolId>`（每协议一份） | `device.state.<deviceId>`（每设备一份） |
| 版本标记 | 无 | `app.schemaVersion = 2` |
| 主题 | `ui.themeMode` | 不变 |

规则：
1. 启动时 `SharedPrefsDeviceRepository.load()` 先调用 `LegacyV1Migrator.migrateIfNeeded()`。
2. 有 v0.1 数据 → 创建默认设备“我的空调”；无 v0.1 数据 → 不创建（空状态）。
3. 旧键不删除，v0.2 不再读写；降级回 0.1 仍可用（但 0.2 中的新改动不会同步回去）。
4. 迁移设备 `pairingConfirmed=false`，首页副标题提示“未做配对测试”，不强制。
5. 未知 protocolId：保存原值，载入时回落首个注册协议并记 WARN。
6. 破坏性变化：`AcMode` 增加 `econo`（追加在末尾，旧 JSON 兼容）；`RemoteRepository` 不再存协议与状态；`RemoteController` 改为每设备一个——相关旧测试需改写。
7. Android 包名与签名不变，覆盖安装可升级。

## 6. 测试清单

详见 [架构 §18](../architecture.md)。要点：

- **domain**：`ac_device_test`、`capability_overrides_test`（交集 / 幂等 / 子集属性 / 保护规则）、`ac_capabilities_test`（中性值归一化）、`capability_explainer_test`、`ac_state_test`（econo）。
- **protocol**：YX1FSF 编码向量（`1D 09 60 50 00 20 00 20`、推导的关机帧 `15 09 20 50 00 20 00 A0`、上游华氏抓包 `1D 09 60 58 00 20 00 A0` 仅解码与校验和）、与 YAW1F 非节能帧逐字节一致、三变体探测帧（`09 0A 60 50 00 20 00 F0` / `09 0A 20 50 00 20 00 F0` / `0D 0A 60 50 00 20 00 30`）、registry 三变体顺序。
- **infrastructure**：设备仓库 CRUD / 排序 / 损坏 / 写失败；`LegacyV1Migrator`（v1→默认设备、仅状态无协议、全新安装、幂等、损坏、中途失败重跑、旧键保留）。
- **application**：向导状态机迁移表逐行；向导控制器（发探测帧、保存前零写入）；`DeviceListController`；`DeviceSettingsController`；每设备 `RemoteController`（隔离、隐藏项帧归一化、设置变更不发码、设备被删事件）。
- **presentation（widget）**：首页空状态 / 列表 / 删除确认 / 重排；向导页完整流程；遥控页无协议下拉且按覆盖显隐；设置页开关与保存；按钮说明。
- **架构 / 版本**：`architecture_test`（新增规则：迁移器仅 infrastructure 内可见；状态机纯净；presentation 不碰 protocol/infrastructure）、`version_test`（0.2.0）。

## 7. 已知限制

- 红外单向：配对测试只能证明某变体能被空调听懂，不能唯一识别型号；YAW1F 与 YX1FSF 的非节能帧相同，若遥控器有“节能”键请手动选 YX1FSF。
- YX1FSF 的 ModelA 行为依据一条上游实机抓包，Econo 模式的功能约束为保守取值，待真机验证。
- 界面状态仍是“假定状态”，用实体遥控器改动后会漂移，下次按键以完整状态重新同步。
